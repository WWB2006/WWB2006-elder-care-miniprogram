## 1. 项目背景与目标

### 1.1 业务背景

行业常用的「9073」口径（约 90% 居家养老、7% 社区养老、3% 机构养老）说明：**绝大多数老年人的照护场景发生在家里，而不是机构内**。这决定了系统的重心不是「机构内部管理」，而是把服务人员、家属、机构三方在**居家场景**中连接起来。

当前三方各自的痛点：

| 角色 | 痛点 |
| --- | --- |
| 老人 | 不会用复杂 App；找不到可信服务；担心陌生人上门；突发情况不知道找谁 |
| 家属 | 无法确认服务是否真的做过；老人健康数据零散；异地无法探望 |
| 服务机构 | 获客靠电话与熟人转介；派单靠微信群；服务过程无留痕，纠纷时无据可依 |
| 社区/监管（延伸） | 服务补贴发放缺少过程数据；服务质量难以抽查 |

> 「9073」为行业通行表述，用于说明市场结构。落地立项前应以项目所在地民政部门的公开数据与政策口径复核。

### 1.2 目标用户与角色

| 角色 | 主要设备 | 使用频率 | 核心诉求 | 本系统承载 |
| --- | --- | --- | --- | --- |
| 老人 | 手机（微信） | 低频但关键时刻高频 | 看得清、点得准、一按就有人 | 老人端分包 |
| 家属（子女） | 手机 | 中频 | 能下单、能看状态、能看健康、能评价 | 家属端分包 |
| 服务人员（护理员） | 手机 | 高频（每天多次） | 快速接单、少填表、打卡简单、钱清楚 | 员工端分包 |
| 机构管理员 | PC 为主 | 高频 | 派单、排班、对账、异常复核 | Web 后台（小程序内只保留看板） |
| 社区/监管 | PC | 低频 | 服务真实性与补贴核销 | 数据导出与只读看板（二期） |
| 客服 | PC + 电话 | 中频 | 纠纷处理、SOS 响应 | 工单系统（二期） |

### 1.3 产品目标与成功指标

**北极星指标**：每月「已完成且被确认」的有效服务单量（体现真实交付，而非下单量）。

| 类别 | 指标 | 目标（上线 3 个月） |
| --- | --- | --- |
| 转化 | 服务详情 → 下单转化率 | ≥ 8% |
| 履约 | 准时上门率（±15 分钟） | ≥ 95% |
| 履约 | 打卡异常率（定位/照片不合规） | ≤ 2% |
| 质量 | 服务完成率（无取消/无争议） | ≥ 96% |
| 质量 | 平均评分 | ≥ 4.7 / 5 |
| 留存 | 家属次月复购率 | ≥ 35% |
| 体验 | 老人端首屏可交互耗时（4G） | ≤ 1.5s |
| 安全 | SOS 从触发到人工响应 | ≤ 60s（值班在线时段） |

> 以上为初版目标值，需结合机构实际供给能力（可用护理员人数、覆盖区域）在第 13 章排期评审时二次校准，避免设定无法交付的指标。

### 1.4 范围界定

**MVP 包含（第 1 期，约 8 周）**

1. 登录与角色分流（老人/家属/员工）；
2. 服务大厅：分类、列表、详情、就近机构；
3. 预约下单 → 微信支付 → 派单/接单 → 上门打卡 → 服务记录 → 确认与评价；
4. 紧急呼叫 SOS（老人端长按触发 + 多通道降级通知）；
5. 健康档案：体征录入、用药提醒、异常提醒；
6. 员工端：任务池、我的任务、打卡、服务记录、排班查看；
7. 管理端（Web）：老人档案、派单、排班、订单与结算、异常复核。

**MVP 明确不做（避免范围蔓延）**

1. 在线问诊、处方流转、医保结算（涉及医疗机构资质与监管，单独立项）；
2. 智能硬件深度联动（跌倒检测、睡眠监测）——MVP 只做蓝牙血压计/手环的**可选**接入；
3. 视频探视——涉及直播类目资质与隐私，列为二期（已有页面占位）；
4. 长护险与政府补贴的自动核销——需与地方平台对接，列在三期；
5. 社交化内容（社区圈子、活动报名）——非核心闭环，二期再评估。

```

    │                   │                    ├─ 接单           │
    │◄── 订阅消息通知 ───┼────────────────────┤                 ├─ 触发订阅消息
    │                   │                    ├─ 到门打卡        │
    │                   │                    │  (定位+照片)     ├─ 防作弊判定
    │◄── 服务中可见 ─────┼────────────────────┤                 ├─ 位置推送(可关)

### 2.4 三个典型用户旅程

**老人（张奶奶，78 岁，独居，视力一般）**

打开小程序 → 首屏第一眼看到红色「紧急呼叫」大字块与「今天的照护」→ 想看服务时点底部「服务」→ 分类用大图标 + 文字（助餐/助浴…）→ 点进详情看价格与服务内容（大字列表）→ 由家属代下单，或自己点「立即预约」→ 页面只有两个必填项（时间、地址）→ 支付页用长按确认按钮。

设计约束：一屏一个主任务；不允许出现「点两次才明白」的入口；任何加载超过 1s 都要有骨架屏与文字提示。

**家属（李先生，45 岁，异地工作）**

通过朋友分享的服务页进入 → 手机号快速登录 → 添加老人档案（姓名、年龄、照护等级、紧急联系人）→ 选择「助医-陪同就医」并下单支付 → 服务当天在订单页看到「已打卡·已到门」与实时位置 → 收到服务记录与照片 → 确认并评价 → 收到本周健康报告。

设计约束：家属端信息密度可以高一些，但**关键状态变化必须通过订阅消息触达**，不能只依赖用户主动打开。

**服务人员（王阿姨，52 岁，使用智能手机但不熟练）**

早上打开小程序（自动进入任务池）→ 看到今日 3 单按时间排序，显示距离与老人标签 → 接单 → 到门后点「打卡」，系统自动定位并要求拍一张现场照片 → 服务完成后逐项勾选服务内容、拍前后照片、输入老人确认码 → 提交，看到「已完成，本单计薪 ¥45」。

设计约束：员工端每一步都要有明确的「下一步」按钮；网络差时要能**离线暂存**服务记录并自动重试上传。

## 3. 技术选型

### 3.1 小程序框架选型对比

| 维度 | 原生小程序 + TS（推荐） | uni-app | Taro | 微信云开发 |
| --- | --- | --- | --- | --- |
| 性能与包体积 | 最优，无运行时开销 | 中（有运行时） | 中 | 最优 |
| 微信能力覆盖 | 100%，新能力第一时间可用 | 好，个别能力需条件编译 | 好 | 100% |
| 多端能力 | 无 | 强（App/H5/支付宝等） | 强（React 生态） | 无 |
| 团队上手 | 会小程序即可 | 需熟悉 Vue + uni 规范 | 需熟悉 React + Taro | 需接受云函数范式 |
| 生态与人才 | 最广 | 广 | 中 | 窄 |
| 适用判断 | 只做微信端、追求稳定与性能 | 已有 Vue 团队且需多端 | 已有 React 团队且需多端 | 小团队、无运维能力 |

**结论：采用「原生小程序 + TypeScript + npm 构建」**。理由：本项目只服务微信端；养老服务对**稳定性与低端机兼容性**要求高；适老化改造需要精细控制渲染与包体积，框架抽象层会带来额外不确定性。若后续确定要上支付宝小程序或 App，再评估迁移（届时 `api/` 与 `utils/` 层可整体复用，页面层重写）。

### 3.2 推荐技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 小程序 | 原生 WXML/WXSS + TypeScript | 开发者工具内置 TS 编译插件（`useCompilerPlugins: ["typescript"]`） |
| 状态管理 | 轻量自研 Store（`store/base.ts`） | 需求集中在用户态与网络态，80 行实现即可；如需响应式可整体替换为 mobx-miniprogram |
| 样式 | WXSS + CSS 变量设计令牌 | 适老模式通过变量覆盖实现，无需两套样式 |
| 图表 | 轻量自绘（`components/mini-chart`）或 ec-canvas 按需引入 | 健康趋势图数据量小，优先避免引入 300KB+ 图表库 |
| 服务端 | Spring Boot 3 + JDK 17 | 国内企业主流，招人容易；若团队偏前端，可选 NestJS |
| 数据库 | MySQL 8（主）+ Redis 7（缓存/锁/会话） | 订单与工单需事务；Redis 承担幂等键与抢单锁 |
| 消息 | RabbitMQ / RocketMQ（订单事件、通知投递） | 先可用 DB 轮询兜底，量级上来再引入 MQ |
| 文件存储 | 对象存储（COS/OSS）+ CDN | 打卡照片、体检报告必须私有桶 + 临时签名 URL |
| 实时 | WebSocket（服务中位置）+ 订阅消息兜底 | 小程序后台保活有限，禁止依赖长连接做关键通知 |
| 地图 | 腾讯位置服务（逆地址解析、距离计算） | 与微信同生态，小程序端接入成本最低 |
| 语音 | 微信同声传译插件（语音识别 / 合成） | 老人端语音输入、播报；需在小程序后台配置插件 |
| 支付 | 微信支付（小程序 JSAPI 下单） | 需企业主体 + 商户号 |
| 监控 | 微信实时日志 + 自建埋点 + 错误上报 | 线上问题定位依赖实时日志，务必在开发期就接入 |

### 3.3 微信平台能力与限制（影响设计的关键点）

| 能力 | 用途 | 限制与应对 |
| --- | --- | --- |
| 订阅消息 | 订单状态、服务提醒、SOS 通知 | 一次性订阅需用户每次授权；长期订阅仅特定行业可申请。**必须设计「授权引导点」**，并在关键节点（下单、接单）主动请求 |
| 客服消息 | 用户在 48 小时内交互后可下发消息 | 仅窗口期内有效，不能作为主通知通道 |
| 手机号快速验证 | 登录绑定 | 必须用户点击按钮触发，不得静默获取 |
| `wx.getAccountInfoSync()` | 判定 dev/trial/release | 环境配置不靠硬编码切换 |
| `fontSizeSetting` | 感知用户系统字号 | ≥22px 时首帧即进入适老模式 |
| 微信「关怀模式」 | 系统级放大 | 小程序无法强制开启，仅能引导：设置 → 关怀模式 |
| 隐私协议 | 敏感接口前置同意 | 2023-09 起强制；`app.json` 需开启隐私校验，未配置将导致定位/相册等接口直接失败 |
| `requiredPrivateInfos` | 位置类接口声明 | 未在 `app.json` 声明会调用失败；需在小程序后台申请对应权限 |
| 代码包体积 | 性能与审核 | 主包 ≤ 2MB、所有分包合计 ≤ 20MB（以官方最新限制为准） |
| 直播组件（live-pusher） | 视频探视 | 需直播类目资质，未取得前不得启用（二期评估） |

## 4. 总体架构

### 4.1 分层架构

```
┌──────────────────────────── 微信小程序（4 个端共用一个包） ────────────────────────────┐
│  页面层 pages / package*                                                              │
│    只做：渲染、交互编排、调用 store 与 api                                              │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  组件层 components（适老化组件库）+ custom-tab-bar                                      │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  状态层 store（用户态/应用态，页面间距数据传递靠 store + 事件总线，不靠 URL 堆参数）        │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  领域层 api（按域拆分）+ utils（请求/鉴权/存储/格式化/隐私/日志）                          │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  基础层 config（常量、路由、环境）+ styles（设计令牌）+ assets + libs                     │
└───────────────────────────────────────────────────────────────────────────────────────┘
                                        │ HTTPS / WSS
┌───────────────────────────────────────▼───────────────────────────────────────────────┐
│  接入层：网关（鉴权、限流、签名校验、TraceId、灰度路由）                                   │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  应用层：auth / elder / service / order / payment / health / staff / notify / sos       │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  领域层：订单状态机、派单策略、排班冲突校验、计薪规则、风控规则                             │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  基础设施：MySQL / Redis / MQ / 对象存储 / 短信 / 微信支付 / 腾讯地图 / 语音外呼            │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 小程序端分包与体积预算

| 包 | 内容 | 体积预算 |
| --- | --- | --- |
| 主包 | 启动页、登录页、4 个 tab 页（首页/服务/订单/我的）、公共组件、utils/api/store/config/styles | ≤ 1.6 MB |
| `packageElder` | SOS、健康档案、用药提醒、语音助手、亲情号码 | ≤ 1.2 MB |
| `packageFamily` | 长辈档案、预约下单、支付、健康报告、视频探视、评价 | ≤ 1.5 MB |
| `packageAdmin` | 运营看板、长者管理、派单调度、异常复核 | ≤ 1.0 MB |
| `packageStaff` | 任务大厅、任务详情、打卡、服务记录、排班 | ≤ 1.2 MB |

控制手段：主包只放 tab 页；图片走 CDN（本地只留图标）；`lazyCodeLoading: requiredComponents` 按需注入组件；`preloadRule` 在首页预下载老人端与家属端分包。

### 4.3 服务端模块划分（建议包结构）

```
com.eldercare
├── config          // 多环境配置、跨域、序列化、线程池
├── common          // 统一响应体、异常、错误码、工具、幂等注解
├── security        // 微信登录、JWT、权限注解、数据脱敏
├── controller      // 只做参数校验与编排，不写业务逻辑
├── service         // 领域服务（订单状态机、派单、计薪）
├── mapper          // MyBatis-Plus Mapper
├── entity / dto / vo
├── job             // 定时任务：超时自动确认、用药提醒扫描、异常工单升级
├── mq              // 事件发布与消费（订单事件 → 通知/计薪/统计）

### 5.3 命名与文件组织规范

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 目录/文件名 | 小写短横线（kebab-case） | `task-pool/`、`elder-button/` |
| 页面文件 | 每个页面固定 4 个同名文件 | `index.ts` / `index.json` / `index.wxml` / `index.wxss` |
| 组件 | 目录名即组件名，内部同样 4 文件 | `components/nav-bar/index.*` |
| 变量/函数 | 小驼峰；布尔值以 `is/has/can` 开头 | `isElderMode`、`hasMore` |
| 类型/接口 | 大驼峰，接口以 `I` 前缀 | `IOrderBrief`、`IStaffTask` |
| 常量 | 全大写下划线 | `PAGE_SIZE`、`SOS_CONFIG` |
| 事件名 | 领域:动作，小驼峰值 | `order:changed`、`sos:triggered` |
| 埋点事件 | 小写蛇形，动词在后 | `service_order_submit`、`task_checkin` |
| 接口路径 | 复数名词 + REST | `GET /orders`、`POST /orders/{id}/cancel` |

分层依赖必须单向：`pages → components`、`pages → store/api/utils`、`api → utils`、`store → utils`。**禁止** `utils` 反向引用 `pages`，也禁止在组件内直接发请求（组件只发事件，由页面调用 api）。

### 5.4 新增一个页面的标准动作（SOP）

1. 在对应分包下建目录（如 `packageFamily/pages/booking/`），补齐 4 个文件；
2. 在 `miniprogram/app.json` 的 `subPackages` 中登记页面路径（**必须登记，否则无法编译跳转**）；
3. 在 `config/route.ts` 的 `ROUTES` 中增加路由常量；
4. 页面根节点绑定 `class="page-root {{elderMode ? 'elder-mode' : ''}}"`；
5. 数据加载走 `api/` 层，空态与错误用 `components/empty-state`，加载用骨架屏；
6. 关键行为调用 `logger.event(...)`；
7. 提交前跑 `npm run type-check && npm run lint && npm run lint:style`。

### 5.5 分包策略说明

| 决策 | 原因 |
| --- | --- |
| tab 页放主包 | 切换 tab 时不能等待分包下载，否则体验断裂 |
| 按角色分包 | 三类用户的功能集互斥，能显著减小各自需要加载的代码量 |
| `preloadRule` 首页预下载 | 老人端/家属端在首页空闲时预下载，点击即开，代价是少量流量（可配置为仅 WiFi） |
| 管理端只保留轻量看板 | 表格、批量操作、导出在 PC 后台体验更好，硬塞进小程序会拖累包体积与开发效率 |

## 6. 关键模块设计

### 6.1 紧急呼叫（SOS）

**这是整个系统里唯一「绝不能失败」的功能**，设计目标不是功能丰富，而是**尽最大可能把呼救信号送出去**。

触发链路（老人端）：

```
首页红色大字块「紧急呼叫」
   └─► SOS 页（全屏、高对比、只有一个按钮）
         └─► 长按 3 秒（震动 2 次 + 进度百分比 + 语音播报「正在呼叫，松手取消」）
               └─► 松手 = 取消（5 秒内不可重复触发，防抖）
               └─► 长按完成 = 触发，进入三通道降级：
                    ① 平台通道：POST /sos/trigger
                       → 后端立刻外呼值班手机 + 推送家属（订阅消息/短信）
                    ② 3 秒内未收到受理回执 → 直接 wx.makePhoneCall 第一紧急联系人
                    ③ 若用户取消拨号或拨号失败 → 全屏展示大号「客服热线」「120」两个一键拨号按钮
```

关键设计决策：

| 决策 | 原因 |
| --- | --- |
| 长按而非单击 | 老人误触率高；长按 + 震动 + 进度反馈把误触率降到可接受范围 |
| 不做二次确认弹窗 | 紧急场景下多一次点击就多一分风险；用「松手即取消」替代确认 |
| 前端也保留拨号能力 | 平台或网络不可用时，系统拨号是最可靠的最后一道防线 |
| 位置上报不阻塞呼救 | 定位失败（权限被拒/室内无信号）时仍立即上报，位置字段留空并标记 `locationMissing` |
| 触发后不依赖 App 前台 | 后端外呼与短信由服务端发起，用户手机没电/息屏也能触达家属 |

服务端响应（SLA）：

| 时间 | 动作 |
| --- | --- |
| T+0s | 落库 `sos_record`，状态 `PENDING`，向值班人员手机外呼 + 家属推送 |
| T+30s | 无人接听 → 升级到机构负责人 |
| T+60s | 仍无人接听 → 升级到区域负责人 + 短信通知全部紧急联系人 |
| T+5min | 标记 `UNRESOLVED`，进入次日复盘清单 |

必测场景：无网络、弱网（1 秒成功 1 秒丢包）、定位权限被拒、联系人号码为空、联系人拒接、小程序被切到后台再回来。

### 6.2 服务预约与订单状态机

```
                         ┌──── 用户取消（未支付）
                         │
 PENDING_PAY ──支付成功──► PENDING_DISPATCH ──派单──► DISPATCHED ──接单──► ACCEPTED
      │                                                                    │
      └──15 分钟未支付──► CANCELED                       打卡成功          │
                                                                          ▼
   REFUNDED ◄──退款完成──┐                                           IN_SERVICE
                          │                                              │
                          │                                        提交服务记录
                          │                                              ▼
                     PENDING_CONFIRM ◄──────────────────────────── PENDING_CONFIRM
                          │                                              │
              用户确认 / 24h 自动确认                                      │
                          ▼                                              ▼
                      COMPLETED ◄────────────────────────────────────────┘
```

规则要点：

| 规则 | 说明 |
| --- | --- |
| 状态只由后端驱动 | 前端任何页面都不得直接修改订单状态；按钮可见性只是「提示」，不是权限 |
| 支付幂等 | 下单携带 `requestId`，支付回调按 `orderNo + 支付流水号` 去重 |
| 超时自动确认 | 服务完成 24 小时后自动确认，避免家属忘记导致服务人员无法结算（需在下单页明示） |
| 取消规则 | 未派单免费取消；已派单且在服务开始前 2 小时内取消，按机构配置收取违约金；服务中不可取消，走客诉流程 |
| 退款 | 原路退回；涉及补贴/长护险的部分需单独标记，不得原路退到微信零钱 |
| 改期 | 二期功能，需重新校验排班冲突并通知服务人员 |

### 6.3 健康档案与体征管理

三种数据来源，优先级从高到低：

1. **设备自动采集**（蓝牙血压计/血糖仪/手环）——数据最准，需老人配合完成一次绑定；
2. **家属/服务人员代录**——上门服务时顺手录入，是 MVP 的主要数据来源；
3. **老人手动录入**——表单要极简（只填两个数字 + 一个大号「保存」按钮）。

异常处理：阈值由机构配置（默认收缩压 ≥ 140 或舒张压 ≥ 90 触发提示），触发后：

- 老人端展示大字提示「血压偏高，请注意休息，必要时联系医生」，**不做医学诊断结论**；
- 同步推送家属（订阅消息 + 短信兜底）；
- 若当日有上门服务，把异常标记推送给服务人员，提示其重点关注。

> 合规红线：小程序内不得出现诊断、处方、用药建议类表述。所有提示文案应为「建议就医/联系医生」的中性表述，最终文案需经合规评审。

健康报告：周报/月报的聚合计算放在服务端，小程序只负责画图。数据量小（每类指标每周 ≤ 30 个点），使用自绘轻量折线图即可，避免引入大体量图表库。

用药提醒：`times` 为每日服药时间点数组，服务端定时扫描并发送订阅消息；老人端首页展示「今天要吃的药」。**提醒只能提醒，不能替代医嘱**，页面需明示数据由家属/机构维护。

### 6.4 服务人员打卡与工单

防作弊四要素（按机构配置组合，至少满足 2 项）：

| 要素 | 采集方式 | 判定 |
| --- | --- | --- |
| 定位 | `wx.getLocation(type: gcj02)` + `accuracy` | 与服务地址距离 ≤ 机构设定阈值（默认 300m）；`accuracy > 100m` 标记可疑 |
| 现场照片 | `wx.chooseMedia` 强制拍照（不允许从相册选） | 后端校验图片 EXIF 时间与上传时间接近 |
| 服务前后照片 | 服务开始/结束各一张 | 缺任一张则服务记录不完整，不能计薪 |
| 确认码 | 老人/家属提供 4 位数字确认码 | 确认码由服务完成时后端动态生成并推送给家属，或记录签字照片 |

异常工单：打卡异常（距离超限、精度过低、重复打卡、同一设备短时间多地打卡）自动生成 `service_anomaly`，进入管理员复核队列，复核结论影响是否计薪。

离线能力（重要）：服务人员的服务地点常在老小区、地下室，网络不可靠。服务记录表单必须支持**本地暂存 + 联网自动重试**（照片先落本地，队列化上传），否则员工会放弃使用小程序。

### 6.5 消息通知体系

小程序消息触达能力有限，因此采用「订阅消息为主 + 短信兜底 + 电话兜底」的三级策略：

| 场景 | 通道 | 兜底 | 说明 |
| --- | --- | --- | --- |
| 下单成功/支付成功 | 订阅消息 | 页面内状态提示 | 用户刚操作完，页面提示即可 |
| 已接单/即将上门 | 订阅消息 | 短信（出发前 30 分钟） | 时间敏感，老人需要提前准备 |
| 服务完成待确认 | 订阅消息 | 无（24h 自动确认） | 失败成本低 |
| 用药提醒 | 订阅消息 | 无 | 每日固定时间；漏服提醒家属可选 |
| 健康指标异常 | 订阅消息 | 短信 | 健康相关，家属必须收到 |
| SOS 触发 | 订阅消息 + 短信 + 电话外呼 | 逐级升级 | 唯一的多通道强触达场景 |

订阅消息的工程要点：

1. **授权点要自然**：下单成功页、订单详情页「开启状态提醒」按钮、SOS 页首次进入时的说明，都是合理的请求时机；
2. 一次性订阅模板每次授权只能推送一次，因此要在**每个需要推送的业务节点重新请求**，不能在启动时一次性索取；
3. 模板 ID 集中在 `config/constant.ts` 的 `SUBSCRIBE_TEMPLATE`，禁止散落在页面里；
4. 长期订阅模板仅特定行业可申请，能否申请到需在小程序后台按实际类目确认，方案上不能假设一定能拿到。

### 6.6 适老化与无障碍设计规范

**目标不是「字大一点」，而是让 70 岁以上、视力与手指精度下降的用户能独立完成核心任务。**

设计令牌（实现见 `styles/variables.wxss` 与 `styles/elder-mode.wxss`）：

| 令牌 | 常规模式 | 适老模式 | 依据 |
| --- | --- | --- | --- |
| 正文字号 | 32rpx | 40rpx | 老人端正文不低于 18pt 等效字号 |
| 标题字号 | 36–44rpx | 44–52rpx | 层级差异必须明显 |
| 行高 | 1.6 | 1.7 | 中文字形复杂，行距不足会导致串行 |
| 主要按钮高度 | 112rpx | 128rpx | 触控目标 ≥ 44pt（约 88rpx），老年用户建议更大 |
| 最小可点击区 | 88rpx | 104rpx | 手指精度下降，误触率高 |
| 图标 | 48rpx | 56rpx | 必须配文字，禁止纯图标入口 |
| 页边距 | 32rpx | 40rpx | 避免内容贴边 |
| 页面层级 | ≤ 3 层 | ≤ 3 层 | 深层级让老人迷路 |
| 正文对比度 | ≥ 4.5:1 | ≥ 7:1 | WCAG AA / AAA 参考 |

十条硬性规则：

1. **图标必配文字**；状态不能只靠颜色表达（如异常同时给文字「偏高」）。
2. 一屏一个主任务，主按钮固定在视觉与拇指可及位置。
3. 关键操作（支付、取消、SOS）使用长按或二次确认，避免误触。
4. 不使用「昨天/3 天前」描述健康与账单，一律给绝对时间。
5. 不出现「加载中」而无反馈超过 1 秒的场景，统一骨架屏 + 文案。
6. 空状态必须给出下一步动作按钮，不能只说「暂无数据」。
7. 错误提示用「发生了什么 + 怎么办」的人话，禁止抛错误码。
8. 支持 200% 系统字号下不截断（布局用 flex/grid，禁止写死高度）。
9. 所有可点击元素提供 `aria-role` / `aria-label`，为后续接入无障碍能力做准备。
10. 每个页面必须支持「返回」和「回首页」两条逃生路径。

发布前检查清单（每个页面过一遍）：在最小屏幕（iPhone SE 尺寸）与最大字号下截图对比；用「眯眼测试」判断主次是否分明；让不熟悉手机的同事盲操作一遍完成核心任务。

### 6.7 状态管理与数据流

```
页面 onLoad ──► store.subscribe / connectStore ──► setData 局部字段
   │                                                      ▲
   ├─► api.xxx()  ──► utils/request ──► 后端             │
   │        └── 成功/失败 ──► 页面 data（列表、表单）      │
   └─► 用户操作 ──► store 更新（跨页面共享）───────────────┘
                        └─► bus.emit 通知其他页面刷新（如订单状态变化）
```

约定：

- 页面私有数据（列表、表单）**放 `data`**，不要塞进全局 store；
- 跨页面共享数据（登录态、角色、当前选中老人、适老模式）**放 store**；
- 跨页面「通知」用 `utils/event-bus.ts`（如订单变更后广播 `order:changed`），页面 `onUnload` 必须 `off`；
- 接口返回的列表统一做**视图层映射**（金额格式化、状态文案），不在 WXML 里写复杂表达式。

### 7.3 数据设计约定

1. **金额一律用「分」存整数**，禁止浮点；
2. **时间统一存 UTC 时间戳或 DATETIME**，展示层按 `Asia/Shanghai` 转换；
3. **敏感字段落库加密**：手机号、身份证号、详细地址、健康指标使用 AES-256 字段级加密，密钥由 KMS/配置中心管理，禁止硬编码在代码里；
4. **逻辑删除**：`deleted_at`，订单与工单禁止物理删除（纠纷取证需要）；
5. **状态与会话**：`order.status` 使用字符串枚举而非数字，避免新增状态导致历史数据歧义；
6. 索引：`order(order_no)` 唯一、`order(elder_id, status)`、`service_task(staff_id, status)`、`health_vital(elder_id, measured_at)`。

## 8. 接口设计规范

### 8.1 通用约定

| 项 | 约定 |
| --- | --- |
| 协议 | 仅 HTTPS（TLS 1.2+），域名必须在小程序后台白名单 |
| 风格 | RESTful，路径带版本：`/elder-care/api/v1/orders` |
| 方法 | GET 查询、POST 创建/动作、PUT 更新、DELETE 删除；动作类接口用子路径（`/orders/{id}/cancel`） |
| 鉴权 | `Authorization: Bearer <accessToken>`；accessToken 2 小时，refreshToken 30 天 |
| 内容类型 | `application/json; charset=utf-8` |
| 分页 | 请求 `pageNum`（从 1 开始）、`pageSize`（默认 10，最大 50）；响应 `list / total / hasMore` |
| 幂等 | 创建类接口必须携带 `requestId`（前端生成），服务端 Redis 存 24h 去重 |
| 时间 | 请求响应统一 ISO 8601（`2026-10-05T14:30:00+08:00`），禁止用「今天/明天」这类相对值 |
| 金额 | 全部为整数「分」，字段名以 `_cents` 结尾 |
| 脱敏 | 手机号返回 `138****8000`，地址默认只返回区/街道级；完整信息仅在授权场景返回 |
| 追踪 | 每个请求带 `X-Trace-Id`，后端日志与埋点可串联，便于线上排障 |

### 8.2 统一响应体

```json
{
  "code": 0,
  "message": "success",
  "data": { "orderId": "1024", "orderNo": "EC202610050001", "status": "PENDING_DISPATCH" },
  "traceId": "k3f9a2-0d81",
  "timestamp": 1791234567890
}
```

失败示例（HTTP 仍可能是 200，业务失败靠 `code` 区分；网络/网关错误才用 HTTP 状态码）：

```json
{ "code": 40100, "message": "登录已过期，请重新登录", "data": null, "traceId": "k3f9a2-0d82" }
```

### 8.3 错误码分段

| 段 | 含义 | 前端处理 |
| --- | --- | --- |
| `0` | 成功 | 正常渲染 |
| `10000–19999` | 参数校验错误 | 定位到字段并内联提示，禁止只弹 toast |
| `20000–29999` | 业务规则拒绝（余额不足、时段不可约、重复下单等） | 展示可执行的补救动作 |
| `30000–39999` | 权限不足（越权访问档案、非本人订单） | 提示无权限，返回上一页 |
| `40100 / 40101` | 未登录 / token 过期 | 自动刷新 token，失败则清会话并引导登录 |
| `42900` | 触发限流 | 提示稍后重试，按钮进入冷却状态 |
| `50000–59999` | 服务端异常 | 统一「服务开小差了，请稍后再试」+ 上报 TraceId |

| 域 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 认证 | POST | `/auth/login` | 微信 code 换取本系统 token，返回角色 |

### 8.5 并发与幂等（最容易出线上事故的地方）

| 场景 | 风险 | 方案 |
| --- | --- | --- |
| 下单 | 弱网重试生成重复订单 | `requestId` + Redis `SETNX` 24h |
| 抢单 | 两名服务人员抢到同一单 | Redis 分布式锁 + 数据库乐观锁 `version` |
| 支付回调 | 微信重复回调导致重复计薪 | `transaction_id` 唯一索引 + 幂等处理器 |
| 打卡 | 重复打卡刷时长 | `task_id` 唯一约束（一人一任务一次有效打卡） |
| SOS | 老人重复触发刷屏 | 前端 5 秒防抖 + 后端 60 秒内合并为同一事件 |

### 8.6 实时通信（服务中位置）

服务进行中，家属可查看服务人员位置。实现方式：`wx.connectSocket` 订阅 `order:{orderId}:track`；每 30 秒推送一次坐标（服务人员端首次需明示并同意）。长连接断开时**降级为 30 秒轮询**，前端不做重连风暴（退避重连，最长 5 分钟）。服务结束即停止采集，位置数据保留 7 天后匿名化。

## 9. 安全、隐私与合规

这一章不是「上线前补文档」，而是**必须前置到需求评审**的约束。踩线的代价是产品下架、罚款与机构资质受损。

> 具体条款适用性与地方口径存在差异，上述判断仅为工程视角的提示，最终结论需法务与当地民政、卫健部门确认。

### 9.2 小程序侧合规动作（上线前必做）

1. 在小程序后台「设置 → 服务内容声明 → 用户隐私保护指引」中如实填写收集的信息类型与用途；未填写将导致定位、相册、手机号等接口调用失败；
2. `app.json` 开启 `__usePrivacyCheck__` 并声明 `requiredPrivateInfos`（本项目代码中已声明 `getLocation / chooseLocation / onLocationChange`）；
3. 敏感信息采用**单独同意弹窗**（`utils/privacy.ts` 已实现 health / location / album / camera / phone 五类），不得与总协议打包默认勾选；
4. 提供**撤回同意**与**注销账号**入口（「我的 → 关怀设置 / 账号与安全」）；
5. 小程序类目与服务内容匹配：涉及医疗服务需《医疗机构执业许可证》；养老服务需相应主体资质与民政备案信息。

### 9.3 技术防护措施

| 层面 | 措施 |
| --- | --- |
| 传输 | 全站 HTTPS（TLS 1.2+），禁止明文放行；小程序端禁用 `urlCheck: false` 上生产 |
| 存储 | 敏感字段 AES-256 字段级加密；密钥托管在 KMS，禁止写入代码与配置文件 |
| 文件 | 打卡照片、体检报告使用**私有桶**，访问走 5 分钟临时签名 URL；禁止公开读 |
| 权限 | 后端始终校验「当前用户 → 目标数据」的归属关系；前端按钮隐藏不作为权限控制 |
| 脱敏 | 列表与详情默认脱敏；查看完整信息需重新鉴权并记审计日志 |
| 审计 | `auth_audit_log` 记录「谁在何时访问了谁的什么数据」，保留 ≥ 6 个月 |
| 位置 | 仅在服务中与 SOS 场景采集；服务结束即停；保留期 7 天后匿名化 |
| 人脸 | MVP **不采集人脸**；若后续用于打卡防作弊，必须单独同意 + 可拒绝替代方案（确认码） |
| 日志 | 日志与埋点自动过滤手机号、身份证、坐标等敏感字段（`utils/logger.ts` 已实现） |
| 员工 | 签署保密协议；员工端离职即注销账号并回收数据权限 |

### 9.4 账号注销与数据删除

注销后：账号立即停用；个人身份信息 15 个工作日内删除或匿名化；订单与服务记录因涉及财务与纠纷取证，按法律要求保留（脱敏后与身份解绑）；需向用户明示保留范围与期限。

## 10. 性能与体验预算

| 指标 | 预算 | 手段 |
| --- | --- | --- |
| 冷启动到首页可交互 | ≤ 1.5s（4G） | 主包瘦身、骨架屏、首屏接口并发、缓存快照 |
| 页面切换 | ≤ 300ms | 分包预下载、避免 setData 传大对象 |
| 列表滚动 | 稳定 60fps | 分页加载、`wx:key` 正确、避免在 WXML 里做复杂计算 |
| 接口响应 P95 | ≤ 500ms | 服务端索引与缓存；列表接口不带大字段 |
| 上传图片 | ≤ 3s / 张 | 前端压缩（`sizeType: compressed`）+ 直传对象存储、多图并发 ≤ 3 |
| 主包体积 | ≤ 1.6MB | 图片走 CDN、`lazyCodeLoading`、移除未用组件 |
| 弱网可用性 | 无网也可看订单与档案 | 最近一次数据落本地（`StorageKey.homeSnapshot`），离线横幅提示 |

`setData` 优化三条铁律：

1. 只传变化的字段路径（`this.setData({ 'list[2].status': 'DONE' })`），不整体重传列表；
2. 单次 `setData` 数据量控制在 256KB 以内，长列表分页；
3. 循环体内禁止连续调用 `setData`（合并后一次提交）。

## 12. 部署与发布

| 环境 | 小程序版本 | 后端 | 数据 | 用途 |
| --- | --- | --- | --- | --- |
| dev | 开发版 | 本地/测试 | 造数据 | 日常开发 |
| uat | 体验版 | 预发 | 脱敏生产副本 | 机构试用、验收测试 |
| prod | 正式版 | 生产 | 生产 | 对外服务 |

发布流程：合并到 `main` → CI 通过 → 自动上传体验版（uat）→ 机构验收 → 提交审核（微信）+ 生产后端灰度 → 审核通过后**分阶段放量** → 观察 24 小时核心指标（启动成功率、接口错误率、支付成功率、SOS 响应时长）。

监控告警（必须配置）：接口错误率 > 1%、支付失败数 > 5/小时、SOS 未响应 > 60s、登录失败率突增、小程序包发布后崩溃率上升。告警接收人明确到人，并配套「谁能回滚」。

回滚：小程序端无法直接回滚已发布版本，因此**关键改动必须靠后端功能开关（`FEATURE_FLAG`）兜住**；后端保持前一版本可回滚部署。

## 14. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| 老人不会用 | 老人端形同虚设 | 高 | 强制适老化规范 + 真人体验测试；核心场景由家属代操作兜底 |
| 服务人员不愿用 | 履约数据缺失，系统空转 | 高 | 打卡流程极简（≤ 3 步）、离线可用、计薪透明、与绩效绑定 |
| 订阅消息授权率低 | 关键通知触达不到 | 高 | 多授权点设计 + 短信兜底 + 重要节点电话 |

### 15.2 脚手架使用说明

1. 用微信开发者工具「导入项目」，目录选择 `elder-care-miniprogram`；
2. 把 `project.config.json` 中的 `appid` 替换为真实小程序 AppID；
3. 执行 `npm install`，在开发者工具中「工具 → 构建 npm」（若使用第三方 npm 包）；
4. 在 `miniprogram/utils/env.ts` 中替换三个环境的接口域名，并在小程序后台配置服务器域名白名单；
5. 在 `miniprogram/config/constant.ts` 中替换客服热线与订阅消息模板 ID；
6. 按 `miniprogram/assets/icons/README.md` 补齐图标资源；
7. 先跑通一个垂直切片（首页 → 服务详情 → 预约 → 下单）再横向铺开。
