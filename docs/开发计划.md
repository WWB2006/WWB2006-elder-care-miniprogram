## 0. 这份计划要解决什么

原设计方案推荐 Java（Spring Boot）后端，实际开发要换成 **Python 后端 + C++ 计算模块**。换栈带来的不是「把 Java 翻译成 Python」这么简单，而是三个新问题：

1. Python 生态跑业务 CRUD 很快，但**计算密集与实时场景不是它的强项**，该由 C++ 补；
2. C++ 一旦引入，就多了一个**构建产物 + 跨语言调用**的复杂度（编译器、交叉编译、序列化、调试），小团队很容易被拖死；
3. 微信小程序**不允许** Python/C++ 直接写界面，C++ 想进小程序只有 WASM 一条路。

所以本计划的核心不是「排一个时间表」，而是：**先用一周把三个技术栈的焊接点验证掉，再决定 C++ 用多重、用在哪。**

## 1. 技术栈定稿

### 1.1 前端（微信小程序）

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 框架 | 原生小程序 + TypeScript | 沿用现有脚手架，不引 uni-app/Taro |
| 状态管理 | 自研轻量 Store（`store/base.ts`） | 已有实现，够用 |
| 样式 | WXSS + CSS 变量设计令牌 | 适老模式靠变量覆盖 |
| 计算加速 | **C++ → WebAssembly（WXWebAssembly）** | 体征信号滤波、异常初判放在端上算 |
| 契约同步 | OpenAPI → 自动生成 TS 类型 | 后端 FastAPI 自动产出 OpenAPI，前端类型不再手写 |

> WASM 的边界：微信小程序通过 `WXWebAssembly` 支持 wasm（基础库 2.13.0+），wasm 文件需随代码包或分包分发，**会占用包体积预算**。跨 JS/WASM 边界的调用有序列化开销，只适合「一次传入一批数据、算完一次返回」的场景，不适合高频小调用。以上约束以微信官方文档为准。

### 1.2 后端（Python）

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 语言/版本 | Python 3.12 | |
| Web 框架 | FastAPI + Uvicorn | 自动生成 OpenAPI，与前端契约天然对齐 |
| 数据校验 | Pydantic v2 | 请求/响应校验，错误码映射 |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 显式事务控制，适合订单类业务 |
| 数据库 | MySQL 8 | 沿用设计方案第 7 章表结构 |
| 缓存 / 锁 | Redis 7 | 下单幂等、抢单锁、refresh token、限流 |
| 异步任务 | Celery + Redis broker | 超时自动确认、用药提醒扫描、通知投递、异常工单升级 |
| 管理后台 | SQLAdmin（复用 SQLAlchemy 模型） | 零额外框架成本；若需要复杂交互再升级为 Vue3 + Element Plus |
| 对象存储 | 腾讯云 COS / 阿里云 OSS | 私有桶 + 临时签名 URL |
| 部署（初期） | Docker Compose + Nginx | 单机即可支撑 MVP，后期再上 K8s |

### 1.3 C++ 模块（三块，按优先级）

| 模块 | 干什么 | 形态 | 优先级 |
| --- | --- | --- | --- |
| 健康信号处理 | 血压/心率/血糖的滤波、去噪、异常初判；把算法放端上，减少上传与隐私暴露 | C++ → Emscripten → **WASM**，小程序内加载 | P0（技术验证第一优先） |
| 派单求解器 | 带约束的指派问题：技能匹配 × 距离 × 排班 × 评价，求全局较优解 | C++ + gRPC 服务（先 pybind11 快速验证，稳定后抽服务） | P1 |
| 设备接入网关 | 血压计、手环、跌倒检测雷达的协议适配与数据上报 | C++ + MQTT / 串口常驻服务 | P2（二期） |

| 工具链 | 选型 |
| --- | --- |
| C++ 标准 | C++20 |
| 构建 | CMake 3.28+ |
| WASM 编译 | Emscripten（emcc，`-O3 -s WASM=1`，导出函数用 `EMSCRIPTEN_KEEPALIVE`） |
| 跨语言调用 | protobuf + gRPC（服务化）/ pybind11（同进程，更简单） |
| 测试 | GoogleTest + CTest |
| 内存检查 | AddressSanitizer（开发期）、valgrind（Linux CI） |

## 2. 目标架构

```
┌────────────── 微信小程序（TS） ──────────────┐
│ pages / components / store / api / utils      │
│            │                                  │
│            │ ① WASM（端上计算）                │
│            ▼                                  │
│   WXWebAssembly ← health_filter.wasm（C++）   │
└──────────────┬───────────────────────────────┘
               │ HTTPS / JSON（OpenAPI 契约）
┌──────────────▼───────────────────────────────┐
│   Nginx（TLS 终止、限流、静态资源）            │
└──────────────┬───────────────────────────────┘
┌──────────────▼───────────────────────────────┐
│   FastAPI（api / services / repositories）     │
│   ├─ 订单状态机、派单、计薪、通知             │
│   ├─ Celery Worker（定时与异步任务）           │
│   └─ SQLAdmin 管理后台                        │
└───┬────────────┬───────────────┬─────────────┘
    │            │               │
    │ ② gRPC     │ SQLAlchemy    │ ③ MQTT
    ▼            ▼               ▼
┌─────────┐  ┌────────┐   ┌───────────────┐
│ C++ 派单 │  │ MySQL  │   │ C++ 设备网关   │
│ 求解服务 │  │ Redis  │   │ （二期）       │
└─────────┘  └────────┘   └───────────────┘
```

**三处技术焊接点**（也就是最容易翻车的三个地方，必须在第 1 周验证）：

1. 小程序 ↔ WASM：C++ 编译产物能否在小程序真机加载并正确返回结果；
2. Python ↔ C++：跨语言调用的契约、错误传递、超时与降级；
3. 前端 ↔ 后端：OpenAPI 契约能否自动生成前端类型，避免手写 DTO 漂移。

## 3. 仓库与目录规划

在现有仓库上扩展为 monorepo（单仓便于展示与一键起环境；微信开发者工具的 `miniprogramRoot` 已指向 `miniprogram/`，不受影响）。

```
elder-care-miniprogram/            # 仓库根（沿用现有目录，不迁移）
├── miniprogram/                   # ① 小程序前端（已完成骨架）
├── server/                        # ② Python 后端（新增）
│   ├── app/
│   │   ├── main.py                # 应用入口、路由注册、异常处理
│   │   ├── core/                  # 配置、日志、安全、依赖注入、错误码
│   │   ├── api/v1/                # 路由：auth / elder / service / order / payment / staff / health / sos / file
│   │   ├── models/                # SQLAlchemy 模型（对应设计方案第 7 章）
│   │   ├── schemas/               # Pydantic DTO（输入输出分离）
│   │   ├── services/              # 领域逻辑：订单状态机、派单、计薪、通知、SOS
│   │   ├── repositories/          # 数据访问，隔离 SQL
│   │   ├── integrations/          # 微信支付、订阅消息、短信、COS、地图、外呼
│   │   ├── tasks/                 # Celery 任务
│   │   ├── admin/                 # SQLAdmin 后台
│   │   └── grpc_client/           # 调用 C++ 派单服务（含降级到规则派单）
│   ├── alembic/                   # 数据库迁移
│   ├── tests/                     # pytest（单测 + 接口测试）
│   ├── deploy/                    # Dockerfile / docker-compose / nginx.conf
│   └── pyproject.toml
├── cpp/                           # ③ C++ 模块（新增）
│   ├── health_filter/             # WASM：信号滤波与异常初判
│   ├── dispatch_solver/           # gRPC：派单求解
│   ├── device_gateway/            # 二期：设备接入
│   ├── proto/                     # .proto 契约
│   ├── cmake/                     # toolchain、Emscripten 配置
│   └── tests/                     # GoogleTest
├── docs/                          # 设计方案 + 开发计划 + 接口说明
├── deploy/                        # 顶层编排（compose 引用 server/deploy）
└── scripts/                       # 一键起环境、WASM 构建、OpenAPI 生成类型
```

关键约定：

- **`.proto` 与 OpenAPI 都是契约文件**，改契约必须走评审并同步前端类型与后端 DTO；
- WASM 产物（`*.wasm`）是构建产物，不入库，由 `scripts/build-wasm.sh` 生成到 `miniprogram/libs/wasm/`；
- C++ 服务与 Python 服务各自独立 Dockerfile，通过 compose 组网。

## 4. 阶段计划

每阶段的「验收标准」是可以当场演示或跑测试证明的动作，不是主观判断。

### S0 · 技术验证与地基（第 1 周）

**目标**：把三个焊接点验证掉，任何一处走不通就地调整方案，避免做到第 8 周才发现 WASM 方案不可行。

| 任务 | 产出 |
| --- | --- |
| S0.1 FastAPI 起服务，`/health` 可用；Docker Compose 起 MySQL + Redis | 本地一键 `docker compose up` |
| S0.2 微信 `code2session` 打通：小程序 `wx.login` → 后端换 openid → 返回 JWT | 登录链路真机可跑 |
| S0.3 Alembic 建首批表：`user` / `elder` / `order` | 迁移脚本 + 建表成功 |
| S0.4 **C++ → WASM PoC**：写一个移动平均滤波函数，Emscripten 编译，小程序内 `WXWebAssembly` 加载并调用 | 真机返回正确结果 + 体积数据 |
| S0.5 **Python → C++ PoC**：pybind11 扩展一个函数，FastAPI 调用成功 | 同进程调用打通 |
| S0.6 OpenAPI → TS 类型生成脚本跑通 | `api/generated.ts` 自动产出 |

**验收**：三条链路各有一次真机/真进程的成功记录，并记录 WASM 产物体积与调用耗时。

**为什么 S0.4 排在最前**：这是整个方案里唯一「可能根本走不通」的技术点（体积超限、内存限制、基础库版本兼容都是真实风险），必须先证伪。

### S1 · 核心业务后端（第 2–3 周）

| 任务 | 关键实现 |
| --- | --- |
| S1.1 分层骨架 | `api → services → repositories → models`，禁止路由里写 SQL |
| S1.2 鉴权 | JWT 双 token、refresh 单飞、权限依赖注入（角色校验） |
| S1.3 服务与时段 | 服务项目、机构、可约时段（排班碰撞校验） |
| S1.4 下单 | `requestId` 幂等（Redis SETNX）、订单状态机集中实现 |
| S1.5 支付 | 微信支付 v3 统一下单、回调验签、`transaction_id` 唯一索引防重 |
| S1.6 派单 | 先规则派单（就近 + 技能 + 排班），C++ 求解器接口**只留桩与开关** |
| S1.7 定时任务 | Celery：超时未支付关单、24h 自动确认、异常工单升级 |
| S1.8 测试 | pytest 覆盖状态机全部分支 + 幂等与并发用例 |

**验收**：`pytest` 全绿；Postman/httpx 脚本能完整跑通「下单 → 支付 → 派单 → 接单」；并发下单测试不会产生重复订单。

### S2 · 小程序前端补齐（第 4–5 周）

现有 27 个页面里只有 2 个是实实现，本阶段补齐用户侧主干。

| 任务 | 页面 |
| --- | --- |
| S2.1 登录与角色 | `pages/login`、家属绑定引导 |
| S2.2 服务大厅 | `pages/service`、`packageFamily/pages/booking` |
| S2.3 订单 | `pages/order`、`packageFamily/pages/pay`、订单详情 |
| S2.4 我的 | `pages/mine`（档案、关怀设置、协议、注销入口） |
| S2.5 基础设施对齐 | `utils/env.ts` 换真实域名；`api/*` 改为引用生成的类型；保留 mock 开关供离线开发 |
| S2.6 适老模式回归 | 所有新页面根节点绑定 `elder-mode`，最大字号下不截断 |

**验收**：真机（至少 iOS + Android 各一台）跑通「看服务 → 选时段 → 下单 → 支付 → 查看订单」，支付用沙箱或 1 分钱订单。

### S3 · 履约闭环与打卡（第 6 周）

这是养老系统真正的价值所在：**证明服务真的发生过**。

| 任务 | 关键实现 |
| --- | --- |
| S3.1 员工端任务池 | 按距离/时间排序；Redis 分布式锁抢单 + 数据库乐观锁兜底 |
| S3.2 上门打卡 | 定位 + 实时拍照 + 精度校验；四要素按机构配置组合 |
| S3.3 服务记录 | 逐项勾选、前后照片、4 位确认码、异常上报 |
| S3.4 文件存储 | 直传 COS 私有桶 + 临时签名 URL；服务端记录 fileId 与业务归属 |
| S3.5 离线容忍 | 断网时本地暂存服务记录与照片，恢复网络后队列化重传 |
| S3.6 异常工单 | 距离超限/精度过低/重复打卡自动入复核队列 |

**验收**：用两个测试账号完成一次真实闭环（A 下单、B 接单打卡提交），后台能看到完整时间线与照片；模拟断网提交后恢复网络能自动补传成功。

### S4 · C++ 深度集成（第 7 周）

本阶段是把「用了 C++」变成「C++ 确实解决了问题」——**必须有可量化的对比数据**，否则面试时讲不出东西。

| 任务 | 关键实现 | 要产出的数据 |
| --- | --- | --- |
| S4.1 WASM 正式版 | 多指标支持（血压/心率/血糖），阈值可配置，提供与 JS 实现一致的接口签名 | 同数据集下 WASM vs JS 纯实现的耗时对比、`health_filter.wasm` 体积 |
| S4.2 端上异常初判 | 在小程序内先判异常，异常才上传明细，正常值只上报聚合结果 | 上传数据量下降比例（预计可显著降低） |
| S4.3 派单求解器 | 带约束指派（技能匹配 × 距离 × 时间窗 × 负载均衡），C++ 实现 + gRPC 暴露 | 求解器 vs 规则派单：平均到场时间、跨区派单率、求解耗时 |
| S4.4 降级策略 | 求解器超时/不可用时自动回退到规则派单，业务不阻塞 | 降级触发次数与成功率 |
| S4.5 性能基线 | 求解器压测（50/200/500 单规模） | P95 响应时间曲线 |

**验收**：能在面试中打开一份对比表，说清楚「为什么这里值得用 C++」「不用会怎样」。

**工程建议**：先用 **pybind11 同进程扩展**快速验证算法正确性与收益；确认有价值后再抽成 gRPC 服务。同进程方案少一次网络往返、少一个部署单元，对单人项目更友好。gRPC 的收益在多语言复用与独立扩缩容，MVP 阶段用不上。

## 5. 前置技术验证（Spike）清单

S0 阶段必须逐条给出「可行 / 不可行 / 需要替代方案」的结论，并写进文档：

| 编号 | 待验证 | 通过标准 | 不通过时的替代方案 |
| --- | --- | --- | --- |
| K1 | C++ 编译的 wasm 能否在小程序真机加载运行 | 真机返回正确结果，冷启动增加 < 200ms | 改用 JS 实现（TS 重写算法），C++ 只保留服务端用途 |
| K2 | wasm 体积是否可接受 | ≤ 300KB（gzip 后更小），不影响主包 2MB 预算 | 移入分包加载；或裁剪算法、`-Os` 优化 |
| K3 | WXWebAssembly 与低端机兼容性 | 目标机型集合 100% 可用 | 能力探测 + JS 降级实现（双实现并行） |
| K4 | pybind11 / gRPC 跨语言调用稳定性 | 异常可正确传递，超时可中断 | 纯 gRPC 服务化；或退化为纯 Python 算法 |
| K5 | 微信支付 v3 回调在本地/测试环境的可行性 | 沙箱或 1 分钱支付成功并可回调 | 用内网穿透 + 测试商户号；实在不可行则 MVP 用「线下支付 + 后台确认」 |
| K6 | 订阅消息模板能否申请到 | 拿到可用模板 ID | 短信兜底为主，订阅消息为辅 |
| K7 | 位置权限与后台定位的合规边界 | 通过合规评审，用户可撤回 | 打卡改为「拍照 + 确认码」，定位仅作辅助 |

## 6. 接口契约的单一事实来源

手写前端 DTO + 后端 DTO 是契约漂移的主要来源。本计划采用单向生成：

```
FastAPI（Pydantic 模型）
   └─► 自动生成 OpenAPI（openapi.json）
         └─► scripts/gen-api-types.sh
               └─► miniprogram/api/generated.ts   ← 前端只做视图层映射，不手写字段
```

规则：

1. 前端**不手工维护**接口字段类型，`api/generated.ts` 由脚本生成，禁止手改；
2. 前端 `api/*.ts` 只做「包装 + 视图映射」（金额转文本、状态转文案），字段本身取自生成类型；
3. 后端改字段 → CI 重新生成 → 前端类型检查失败 → 强制同步，问题在编译期暴露而不是线上；
4. 契约变更需要版本化：破坏性变更走 `/api/v2`，不破坏老版本客户端。

## 7. 测试策略

| 层次 | 工具 | 覆盖目标 |
| --- | --- | --- |
| Python 单测 | pytest + pytest-asyncio | 订单状态机全分支、幂等、并发抢单、权限校验；覆盖率 ≥ 70% |
| 接口测试 | httpx AsyncClient | 每个接口的正常路径 + 至少 2 条异常路径 |
| C++ 单测 | GoogleTest + CTest | 滤波算法边界值、求解器约束满足性；覆盖率 ≥ 80%（算法层必须高） |
| WASM 一致性 | 同数据集双跑 | WASM 结果与 JS 参考实现逐点比对，误差在容差内 |
| 前端组件 | miniprogram-simulate | 适老按钮长按、空态、自定义 tabBar |
| 契约测试 | OpenAPI 校验 | 后端响应结构与 OpenAPI 一致 |
| 越权测试 | pytest 参数化 | 每个涉数据接口至少 1 条越权用例 |
| 真机与适老 | 人工 | 目标机型矩阵 + 5 位 65+ 用户实测 |

**每个阶段的 Definition of Done**：功能可演示 + 测试通过 + 无 P0/P1 缺陷 + 接口契约已同步 + 埋点已加 + 适老模式已适配。

## 8. CI/CD

```
push / PR
  ├─ 前端任务：npm ci → type-check → lint → lint:style → 单测 → OpenAPI 生成类型比对
  ├─ 后端任务：uv sync → ruff → mypy → pytest（含 MySQL/Redis 服务容器）→ 迁移脚本校验
  └─ C++  任务：cmake 构建 → GoogleTest → Emscripten 构建 wasm → 产物体积阈值校验
merge to main
  ├─ 构建镜像并推送
  ├─ 部署到 uat（docker compose）→ 冒烟测试
  └─ 上传小程序体验版（miniprogram-ci）
```

体积阈值校验值得单独做：`health_filter.wasm` 超过 300KB 就让流水线失败，避免包体积在几个月里悄悄膨胀。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| WASM 在小程序端体积超限或兼容性差 | S4 前半段作废 | S0.4 先验证；准备 JS 参考实现与能力探测降级 |
| C++ 引入的构建复杂度拖慢迭代 | 每改一行算法都要过编译链 | 算法与业务彻底解耦（纯函数 + 固定接口）；WASM 构建脚本化，产物不入库 |
| 跨语言调用增加故障面 | 线上问题定位困难 | 调用必须有超时与降级；错误码统一；生产默认走规则派单 |
| 求解器收益不明确 | 白做 | 先定义评价指标（平均到场时间/跨区率），跑 A/B 对比，无提升就不上生产 |
| Python 性能不足以支撑成长期 | 后期重构 | 接口层异步化 + Redis 缓存 + 慢查询治理；真瓶颈才下沉到 C++ |
| 双语言栈人力要求高 | 招人难、维护贵 | 单人项目时 C++ 只保留 WASM 一块，其余用 Python |
| 微信侧资质与模板审核 | 关键能力不可用 | W1 就启动类目与模板申请，不放到上线前 |
| 一键三技栈的环境搭建成本 | 协作效率低 | `docker compose up` 一条命令起 MySQL/Redis/后端；前端与 C++ 各自脚本化 |

## 13. 每周节奏与协作约定

| 项 | 约定 |
| --- | --- |
| 周节奏 | 周一确认本周验收标准；周三中间检查；周五演示可运行的东西（不接受「快好了」） |
